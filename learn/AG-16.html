Framework Selection

Framework choice is a two-to-three-year bet. Choose with a matrix, a bake-off, and an exit plan — not a demo-day feeling.

▶ Watch this reel

What you'll learn

  1. The selection matrix
  2. Lock-in & portability
  3. The hands-on bake-off
  4. Decision discipline

Remember this

  • Weight the boring axes: control-flow philosophy, ecosystem, maturity pulse — features converge, these don't
  • Keep a plain, testable core with the framework as a shell and protocols (MCP/A2A) as integrations — the exit costs a re-shell, not a rebuild
  • Run the same-task bake-off on honest dimensions, record the ADR with tripwires, and re-ask 'would we choose this again?' every quarter

Matrix (weight boring axes)

  • Control (who owns flow) · ecosystem (docs, hiring, 2 a.m. answers) · language/runtime fit · maturity pulse (cadence, spec absorption).
  • Features converge — philosophies and momentum don't.

Lock-in & portability

  • Lock-in layers: model bindings (cheap) · tool integrations (cheap if MCP) · orchestration logic (expensive).
  • Shell pattern: plain tested core + framework at edges + protocol integrations.
  • Write the exit plan at adoption.

Bake-off

  • Same representative task (tool + branch + failure + checkpoint) in top-2.
  • Dimensions: time-to-working, my-code ratio, break-it debugging, test ergonomics, free observability.

Discipline

  • ADR + pre-agreed tripwires + quarterly 'would we choose this again?' — switch bravely.
